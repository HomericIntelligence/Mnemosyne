# A Merged Capability Is Dormant Until The Launcher Publishes It

## Overview

| Field | Value |
| ------- | ------- |
| **Date** | 2026-11-28 |
| **Objective** | Turn on an optional service capability (for example a remote TLS listener) that is merged but never configured in production. |
| **Outcome** | Operational. The capability stayed off for weeks because the one launch path never passed its settings. After the launcher read a durable bundle record, the capability worked from a second node. |

## When to Use

- The code has the capability, but the live service record (the file the service publishes for its clients) shows it absent or null.
- Clients fail with a message that blames the client side (for example "use another host") while the server side has no setting for the capability.
- A launcher script is regenerated by start, move, rollback, or a scheduler job from only the deployment context, so a flag that one step passed is lost.
- You must choose which release tree restarts a live service, and the deployment context is registered per installation.

## Verified Workflow

### Quick Reference

```text
1. Read the LIVE published record. Absent block = dormant. Do not trust the merged code.
2. List every code path that builds the service command: generated launcher,
   hand start, legacy script, move, rollback. One path fixed is not enough.
3. Keep settings in a durable record beside the files the launcher reads
   (one generation directory + one pointer), not in a flag on one start step.
4. The launcher adds the flags only when the whole bundle exists, and computes
   the host name when it runs (the service can move).
5. A bad or missing bundle degrades the optional capability only. The service
   still starts. The pre-bind safety check stays: never listen with unsafe files.
6. Prove it from a node that is NOT the service host, with a command that
   needs the service (a status call that reads shared files proves nothing).
```

### Suggested Approach

**Settings location.** A launcher is rebuilt by every start, move, and rollback from the smallest input those paths have, usually the deployment context. A setting that only one release step passes is lost at the next move. Put the setting (for example the port) in a record inside a versioned bundle directory. Switch one pointer (a symlink) to publish a new bundle. The launcher reads the pointer when it runs. Then a re-issue needs no launcher rewrite.

**Certificate names.** The client checks the server name it dials. Use the name the launcher computes at run time (the short node name when that is what resolves). A wildcard does not match a short name, so list one explicit name per node that can host the service. A list of about a thousand names produced a certificate of about 22 KB that a standard TLS library verified. Re-issue after the cluster gains nodes. Log a warning at start when the local name is not in the certificate.

**Retention.** A running service publishes the real path of its CA file. Do not prune bundle generations by count: a few re-issues delete the file a running service points to, and the route fails with no start event. Prune by age, never remove the generation the pointer names, and state the restart window in the docs.

**Choosing the tree.** A deployment-context registry belongs to one installation. A CLI of another tree cannot select or restart a service of this tree, and a launcher that bakes in a scratch checkout path breaks when that checkout is deleted. Restart a live service only from a tree that owns the registered context and holds the fix. If the owner limits the release in flight, get the fix into that release tree by promotion. Do not run the newer release tree to get the feature. Read-only probes are fine.

**Rehearsal.** Prove the capability on the non-production lane first. Before you replace a service there, check whether someone runs a rehearsal on it; a hand-started service is easy to break.

**Degraded start.** A check that refuses to start the service when an optional file is unsafe turns a certificate problem into an outage after the next move. Keep the check before binding, but make the result "optional capability off", visible in status and in any dry-run check output.

## Failed Attempts

| Attempt | What Was Tried | Why It Failed | Lesson Learned |
| --------- | ---------------- | --------------- | ---------------- |
| Port as a start flag | Pass the port to the one release step that starts the service. | A later move or rollback rebuilt the launcher from the context only and dropped the route. | Persist settings beside the bundle that the launcher re-reads. |
| Prune by count | Keep the newest three bundle generations. | A running service published a path in an older generation, and three re-issues deleted it. | Prune by age and never the pointed generation. |
| Restart from a scratch checkout | Run a main-branch CLI against the context of the running tree. | The context registry belongs to the installation; the selection was refused, and a baked scratch path would later vanish. | Restart from the tree that owns the context and holds the fix. |
| Status as proof | Run a status command from another node and see data. | The client read shared files and never used the service route. | Probe with a command that needs the service. |
| Hard refusal on bad files | Exit when the optional key file has unsafe modes. | A move would leave no service. | Degrade the capability, keep serving locally. |

## Results & Parameters

### Configuration

```text
bundle/<generation>/{ca, certificate, key, record}   # key mode 0600; ca 0640
bundle/current -> <generation>                        # one atomic pointer switch
retention: keep generations younger than 30 days + the pointed one
launcher: if all files exist and record parses -> add 5 flags, host=$(hostname -s)
          else -> start without the capability
```

### Expected Output

- The live published record contains the capability block with the node name and port.
- A read-only service call from a second node returns success. Before the change it returned the "unavailable" exit.
- After a move, the record names the new node and the same probe still passes.
