# Reproducible BF16 CUDA Monokernel SOL Profiling and Optimization

## Overview

| Field | Value |
| --- | --- |
| Date | 2026-08-03 |
| Objective | Measure and iteratively optimize latency-oriented BF16 CUDA monokernels without conflating model naming, correctness, profiler overhead, isolated-position wins, or global hardware roofline utilization. |
| Outcome | A 14-case RMSNorm H200 matrix established the reproducible profiling contract. A later full-decoder campaign added immutable attempt commits, five-position minimax acceptance, conditional reconsideration triggers, resource-state audits, compiler-materialized composition decisions, and periodic durable-learning checkpoints. |
| Verification | verified-local: rootless image contracts and full host suites passed; H200 GPU validation and Compute Sanitizer passed; the RMSNorm Nsys matrix and the full-decoder five-position screens and confirmations retained artifact hashes, exact source bindings, static-resource reports, and harness-owned correctness evidence. |

## When to Use

- A CUDA microkernel should represent model normalization-module parameter sizes rather than a model's total parameters or an entire transformer layer.
- Multiple representative models map to the same RMSNorm or LayerNorm parameter count and would otherwise create duplicate benchmark rows.
- A low-latency BF16 kernel needs independent baseline comparison, exhaustive correctness checks, and a reproducible rootless H200 environment.
- A roofline report must distinguish an algorithmic lower bound from native Nsight Compute counters and Nsight Systems timing attribution.
- Nsight Compute fails with a GPU-counter permission error, but a valid Nsight Systems trace can still be collected.
- A one-row kernel has very low global SOL and an optimization decision must distinguish launch/grid underfill from poor HBM use.
- A full monokernel has several required sequence positions and the slowest relative-to-roofline position, rather than one favorable position, must control acceptance.
- An optimization lost under an earlier champion, but a later fusion, attention algorithm, register count, shared-memory layout, or phase balance may have removed the reason it lost.
- A source-level optimization, isolated prototype, register count, or SASS instruction count predicts one outcome while the fully composed candidate measures another.
- A hot online scan carries a small state in registers, and a proposed shared-memory or hybrid split is expected to reduce register pressure.
- A refactor lowers SASS instruction or register counts but changes independent memory issue, address lifetime, or the hot dependency chain.
- A logically redundant predicate or equivalent source-level control rewrite leaves register and instruction counts unchanged but materially changes measured latency.
- A source-level attempt to narrow an index or partially unroll a fixed-trip loop is expected to reduce liveness, but the linked kernel instead allocates more registers or stack-backed local state.
- Several losing combinations share one mutually exclusive implementation, and the campaign needs to distinguish that common replacement's cost from its partners' interactions.
- A partner changes the linked binary and improves over a losing control, but the full composition still does not beat the accepted champion.
- An address-space-specific intrinsic is transplanted while the pointer still resolves to storage from a mutually exclusive implementation.
- A composition removes cold alternatives and lowers whole-binary instruction or register totals, but matched latency gets worse.
- A focused source contract passes, but the modified helper is unreachable under the benchmarked dispatch and the compiler removes it from the linked image.
- A multi-mechanism source composition is distinct from its parent but may collapse to the exact linked binary of an earlier subset candidate.
- A BF16 pair-conversion idea may also change transport, lane ownership, score dependencies, or value-update lifetime.
- A long optimization campaign needs permanent RED/GREEN/outcome evidence and a fixed cadence for consolidating reusable lessons.
- Several benchmark or profiler launchers share one physical GPU, and a lock name or scheduler lane alone may not prove exclusive compute use.

## Verified Workflow

### Quick Reference

1. Derive each workload from one source normalization module and deduplicate by total learned parameter count.
2. Keep baseline and optimized CUDA implementations separate; make the host harness own input generation, timing, exhaustive comparison, and failure policy.
3. Verify the rootless image digest before creating the runtime, then record image, dependency-lock, source-tree, device, tool, and profiler artifact hashes.
4. Measure verified uninstrumented p50 first. Capture a separate Nsys trace for kernel duration and launch attribution; collect NCU counters only when permitted.
5. Report algorithmic, NCU, and Nsys SOL as separate fields. Interpret global SOL together with CTA-to-SM coverage.
6. For multi-position kernels, accept against the minimum SOL across the required positions and preserve the exact candidate revision, screen, and confirmation separately.
7. Treat rejection as conditional. Record why it lost and an objective trigger for reconsideration, then audit those triggers after every accepted champion.
8. Rank evidence in this order: runnable fully composed binary, host-owned correctness, matched short screen, then long confirmation. Resource metrics diagnose the result; they do not reject a runnable candidate.
9. Rebaseline the champion after moving to a different node or shared execution lane; serialize qualification on one pinned physical GPU and compare candidates only with evidence collected under that lane.
10. Treat a historical regression threshold as an experiment-selection rule only. Before combining rejected mechanisms, bind each exact source delta, eliminate no-ops and mutually replacing variants, and measure the fully composed binary rather than adding their individual percentages.
11. Treat register-to-shared state migration as a new full-kernel experiment: inspect the linked allocation and time it, because shared base pointers and indices can lengthen live ranges enough to increase registers.
12. Preserve useful overlap when reducing instructions: separately inspect dependency depth, independent K/V issue, and persistent 64-bit address state before treating a smaller binary as an optimization.
13. Treat source-equivalent control flow as a compiler-scheduling experiment: compare exact linked SASS identity and ordering as well as aggregate counts, then decide from matched correctness and timing.
14. Verify scalarization after every index-width or unroll change. Partial unrolling can preserve runtime-indexed arrays and force stack-backed local traffic where full unrolling scalarized every element; a narrower source integer can also lengthen surrounding values' live ranges.
15. Prove each mechanism remains active in source and in the benchmark-selected linked path. If a named mechanism changes only an unreferenced alternative and the exact linked SASS is byte-identical to a measured parent, invalidate it as a duplicate implementation before GPU timing. This is identity deduplication, not a static-performance rejection; every distinct runnable binary still requires matched correctness and timing.
16. When several combinations share one alternative implementation and lose, run the smallest control composition that preserves the champion's other mechanisms. Attribute the dominant cost only after comparing that control's linked identity and matched timing.
17. Compare a composition against two explicit references: the accepted champion decides promotion, while the simplest shared-replacement control explains whether the partner worsened, compiled away, or partially rescued the common cost.
18. Bind address-space-specific loads to the actual storage path. Prove that mutually exclusive staging was removed and that the pointer reaching the intrinsic has the intended address space before GPU qualification.
19. Segment static evidence by selected hot path. Whole-binary decoded instructions include cold or unreachable alternatives; deleting them can shrink aggregate SASS while adding cost to the path selected by the benchmark. Compare phase and path-local issue, recurrence, and memory behavior before interpreting a global count.
20. Key every interaction label to the exact parent and full composition. A mechanism that partially rescues one losing control is not globally beneficial: with a different partner or inherited schedule it can become neutral, compile away, or amplify the loss. Carry the source and binary identities in the interaction record, and require a fresh champion-relative screen before reusing labels such as rescue or harmful.
21. Separate candidate identity from candidate adjudication. Source presence alone does not create a new implementation: bind dispatch reachability, compiler diagnostics, and linked SASS before GPU work. Correctness and performance remain the only acceptance or rejection metrics for distinct runnable implementations.
22. Deduplicate linked implementations against the full campaign, not only the immediate parent. When one tuple member is compiler-eliminated, the result can equal a previously measured subset candidate even though it differs from the parent and source composition. Record the tuple as invalid with the surviving subset identity and skip repeated correctness or timing.
23. Separate a reachability control from a mechanism implementation. Redirecting a workload to an older helper can prove that a historical delta materializes, but it simultaneously changes dispatch topology and therefore cannot isolate the mechanism's value. Preserve the accepted dispatch for the optimization candidate, implement an equivalent lowering in every selected active path where the geometry is valid, prove path-specific source activation and linked reachability, and measure that composition independently.
24. Decompose BF16 pair conversion into transport, logical lane ownership, score-path dependency, and value-update lifetime. Preserve the accepted transport and ownership first, then screen key-only and value-only conversion controls separately. A value pair constructed after score reduction can remain worth reconsidering even when key-only or combined packing loses.
25. Bind numerical validation to reduction topology as well as nominal precision. Higher-precision state, two-pass softmax, and vectorized framework reductions can each move BF16 rounding in a different direction. Validate every required context boundary against the same trusted reference and compare every produced cache element. When two implementations disagree, qualify each independently against that reference before treating either one as the oracle.
26. Treat physical-GPU isolation as measured state, not a launcher convention. Every process that can use one physical device must share one canonical UUID-keyed lock. While holding that lock, require a zero-compute-process audit immediately before timing. If scheduler history or process evidence proves overlap, invalidate the timing, preserve correctness only as diagnostic evidence, and rerun in a new result root after every overlapping process is terminal.

### Detailed Steps

1. **Map model normalization parameters, not model size.** Map RMSNorm width `H` to `H` learned parameters, affine LayerNorm to `2H`, and bias-free LayerNorm to `H`. A parameter-count-equivalent RMSNorm workload must retain the source normalization type and must not claim to execute LayerNorm semantics.
2. **Make the execution ladder canonical.** Select exactly one representative case for each total parameter count. Keep other models with an equal count as provenance aliases only; do not give them independent CLI identifiers, profiler directories, or correctness results.
3. **Keep validation outside CUDA implementation code.** Generate deterministic BF16 inputs and non-unit weights in the harness. Run independent baseline and optimized implementations on identical inputs, compare every output, record nonfinite and error statistics, and run a small host oracle. Return CUDA errors to the harness instead of embedding device-side assertion policy.
4. **Create a reproducible rootless profile environment.** Pin the dependency lock and SquashFS image; verify image bytes by SHA-256 before rootless runtime creation. Mount source and a dedicated result directory, record device and tool versions, and make a post-run provenance document hash every retained benchmark and profiler artifact.
5. **Separate timing from tracing.** First run a verified, uninstrumented benchmark with stable warmup and sample counts. Then use a short `nsys` or `ncu` capture to identify the optimized kernel. Do not treat profiler-instrumented host timing as the latency benchmark result.
6. **Compute the algorithmic lower bound explicitly.** For `N = rows * columns` BF16 weighted-RMSNorm elements, use `F = 4N` FLOPs and ideal traffic `B = 6N` bytes for one input, one learned scale, and one output. With the selected hardware profile, calculate `T_SOL = max(F / peak_compute, B / peak_memory)` and `runtime_SOL = min(T_SOL / verified_p50, 1) * 100`.
7. **Keep three profiling views distinct.** Report algorithmic/runtime SOL from the uninstrumented p50; report NCU counter SOL as the greater of DRAM and SM percent-of-peak only when counters were collected; and report Nsys average kernel duration, estimated launch gap, and a separately calculated kernel-only lower-bound SOL. The harness's implementation-specific traffic convention is not the ideal roofline byte count.
8. **Fail closed on missing NCU access.** If NCU returns `ERR_NVGPUCTRPERM`, record counter SOL as unavailable and preserve the failure reason. Do not report zero utilization or bypass host policy. Use Nsys to preserve kernel duration and launch attribution, while clearly stating that it does not measure native bandwidth or SM utilization.
9. **Interpret grid coverage before choosing an optimization.** Include `min(grid_blocks / SM_count, 1)` in every report. A one-CTA workload cannot saturate all SMs, so a low global SOL can primarily indicate launch overhead or underfill. To improve single-invocation latency, prioritize launch reduction or legal fusion; increasing concurrent work changes the workload and should be reported separately.
10. **Use a minimax acceptance objective for required positions.** Define the legal position set before optimization and keep it fixed. Screen every immutable candidate with the same warmup, iteration count, grid, image, model pack, and fixtures; only promote a candidate that improves the minimum required-position SOL without an unacceptable regression elsewhere. Confirm a screen winner with a longer run before changing the champion. Never substitute a prototype result for the exact formal revision.
11. **Make every rejection conditional and triggerable.** Store the mechanism, tested champion, controlling position, measured failure, resource state, and a measurable recheck trigger. After each accepted champion, audit position timing, phase attribution, registers, stack, spills, local memory, static and dynamic shared memory, occupancy, and legal grid ceiling. Recompose and rescreen a dormant mechanism when its trigger fires. A prior no-go is evidence about one composition and one bottleneck state, not a permanent property of the mechanism.
12. **Keep an immutable campaign ledger.** Give each formal attempt permanent RED, GREEN, and outcome commits. Bind reports to Git revision plus every included CUDA/header blob that changes generated device code. Preserve raw results outside Git by immutable path, scheduler ID, and SHA-256. Record conditional prototypes separately so a recheck does not silently consume a formal iteration or rewrite history.
13. **Checkpoint reusable knowledge at a fixed cadence.** Decide the cadence before the campaign; the verified full-decoder campaign used every five formal attempts. Do not mark the boundary attempt complete until the learning disposition and, for a write disposition, the resulting knowledge PR URL are recorded. This keeps the campaign ledger and the durable rule synchronized without treating every noisy prototype as a new skill.
14. **Judge the compiler-materialized full composition.** Build the exact candidate with every selected mechanism enabled and inspect its emitted resources and SASS. Record registers, stack, compiler-reported spills, local instructions, shared memory, residency, launch ceiling, and device-code identity, but do not use a resource threshold to reject a runnable candidate or suppress timing. An illegal launch or kernel that cannot complete is an execution failure, not a resource-metric verdict. Host-owned correctness and matched performance are the only rejection metrics. A power-of-two geometry or occupancy change may win despite more registers, local traffic, or instructions when it removes tail work, branches, or synchronization; limited spilling may likewise trade favorably against occupancy or scheduling. Change the champion only after the same immutable candidate passes correctness, matched screens, and long confirmation. Re-evaluate each mechanism after composition because independent or short-screen gains are not additive.
15. **Use a staged noise gate for layout-sensitive candidates.** Reject immediately when the first fixed-position matched screen loses. When the mechanism changes whole-kernel layout without changing legal occupancy, require two independent positive screens before spending the full-position budget; then treat the longer confirmation as authoritative even if both screens won. Bind each screen and confirmation to its exact scheduler execution and device-code identity. A register or SASS reduction that does not cross an occupancy or launch ceiling is diagnostic evidence, not an expected speedup.
16. **Replay a queue against the evolving champion.** When reconsidering several rejected mechanisms, compose the first onto the current champion and promote it only after full confirmation. Use that newly accepted composition as the parent for the next replay. Do not evaluate the whole queue independently on one stale base: the first accepted replay can change code layout, live state, and bottlenecks enough to reverse the next mechanism. Preserve each original result and record every replay as a new formal attempt; a replay does not rewrite history or guarantee related variants will also win.
17. **Rebaseline after an execution-lane change.** A shared non-exclusive allocation is valid for latency qualification only when campaign jobs are serialized on one pinned physical GPU and the accepted champion is measured there before the next candidate. Record the node, GPU UUID/index, co-tenant process or utilization snapshot, and lock identity. Do not compare a shared-lane candidate with a confirmation from another node or an earlier dedicated allocation: even identical H200 SKUs can differ through clocks, thermals, power sharing, and concurrent host activity. The lock prevents campaign self-interference; it does not make changing co-tenants disappear, so keep the baseline and candidate temporally adjacent and repeat noisy winners.
18. **Design rejected-mechanism combinations as new experiments.** A threshold such as "at least one prior screen lost by less than one percent" may prioritize candidates, but it must never relax correctness or promotion. Recover the exact optimization delta rather than the whole historical file, classify whether two deltas are additive, mutually replacing, or exact no-ops on the current champion, and prefer orthogonal pairs that target different live ranges or phases. Give every pair a new immutable attempt and compiler-materialized identity. Compile and run focused source contracts before GPU qualification because a later champion may have removed constants, helpers, includes, or other dependencies that the old delta assumed. Do not predict the pair by adding individual latency percentages: composition can change inlining, register allocation, instruction layout, and the controlling path. Promote only from unchanged host correctness and matched confirmed performance.
19. **Measure online-state placement as a liveness composition.** For a small state updated on every scan iteration, compare an all-register schedule and any shared or hybrid schedule as separate immutable candidates. A shared split does not remove the pointer, address arithmetic, predicates, or update temporaries needed to access that state; those values can overlap the remaining register state and increase the linked register allocation even when the source declares fewer arrays. Keep the hot state in registers when that removes per-iteration loads, stores, or broadcasts and the confirmed minimax result wins. Reconsider shared placement only with a new layout that shortens address lifetimes or amortizes publication, and never infer the outcome from source variable count.
20. **Treat instruction reduction and overlap as separate objectives.** When combining independent K/V load loops, staging several scores before updates, or hoisting a cache-address base, draw the before-and-after dependency graph as well as counting SASS. A fused load loop can serialize otherwise independent memory issue; a score array can delay the recurrence that controls online reduction throughput; and a persistent 64-bit base can overlap the whole loop and expand allocation even though it removes source arithmetic. Preserve independent issue and short address lifetimes unless the exact linked candidate proves a better schedule. Record decoded instructions and registers as explanation, but let unchanged correctness and matched timing decide.
21. **Freeze and time source-equivalent control rewrites.** A redundant bound check, reordered predicate, explicit unrolling, or lexical-scope rewrite can act as a compiler scheduling boundary. Equal register counts, spill counts, shared memory, and decoded instruction totals do not prove equal instruction ordering or dependency behavior; even a byte-identical aggregate resource report can accompany a materially different SASS stream. Bind the exact device code, inspect ordering or hash changes, and run the same matched screen. Retain the original spelling when the rewrite loses, even when the new source is logically simpler.
22. **Audit scalarization instead of inferring liveness from source types.** For a fixed-trip loop over small register-intended arrays, compare full, partial, and explicit unroll directives as separate compiler-materialized candidates. Inspect stack size and linked local load/store sites as well as register count: partial unrolling may retain dynamic indexing and materialize the arrays in thread-local stack memory, while an explicit full-trip directive can preserve aggregate counts yet change scheduling. Likewise, replacing a bounded address expression with a narrower integer can expand allocation when conversions or surrounding address values stay live longer. These are diagnostic failure signatures, not static rejection gates; execute every runnable candidate and let unchanged host correctness plus matched performance decide.
23. **Bind composition identity at both source and binary levels.** Recover each mechanism as an exact delta and anchor its focused contract to the intended phase or helper, because similar source regions can make a broad replacement activate the wrong path. After building, bind the selected dispatch path, compiler diagnostics, linked device-code hash, and resources. When a named mechanism is absent from the linked implementation and SASS is byte-identical to a measured parent, record an invalid duplicate without GPU timing; there is no distinct implementation to adjudicate. Do not generalize this identity rule into a resource gate: two distinct runnable binaries with equal aggregate counts still require unchanged correctness and matched timing. Conversely, two individually near-neutral deltas can become either a clear regression or a confirmed improvement after composition. Advance the champion only after full confirmation, then re-audit every remaining tuple against that new source and binary identity.
24. **Use a control composition to localize a shared regression.** If multiple losing tuples all replace the same mutually exclusive implementation, freeze the simplest candidate containing that replacement plus only the champion's already-accepted mechanisms. Run unchanged correctness and the matched screen before attributing losses to partner interactions. If the control also loses, treat the common replacement as the current dominant cost and lower the priority of further combinations that cannot remove that cost. If a later partner variant emits byte-identical SASS to the already measured control, record it as a compiled-away invalid duplicate rather than spending another GPU screen or attributing lane variance to that partner.
25. **Separate acceptance from interaction diagnosis.** For every composition built on a losing shared-replacement control, report two deltas from matched evidence: candidate versus accepted champion, and candidate versus that control. Only the champion-relative result can promote or reject. The control-relative result classifies the interaction: byte-identical device code means compiled away; a distinct binary that narrows the control's loss is a partial rescue; and a larger loss is a harmful interaction. A partial rescue that remains slower than the champion is still rejected, but it is stronger reconsideration evidence than a partner that compiled away or worsened the control. Reconsider it only after an objective trigger changes the remaining shared cost.
26. **Validate address space after mutually exclusive composition.** Intrinsics such as read-only global loads are not source-text properties: their legality depends on the pointer's materialized storage path. When replacing one table implementation with another, require a focused contract that proves the old shared or local staging declaration, copy, and call-site argument are absent; prove the global pointer reaches the intrinsic; then execute host-owned validation. A candidate can compile successfully yet fail when the intrinsic receives a shared-memory address. Classify that as an invalid composition, recover only the intended deltas, and retry without consuming the invalid result as performance evidence.
27. **Audit active-path reachability before qualification.** A source contract can prove that a delta is spelled correctly while missing that dispatch selects another helper for the measured workload. Compile the frozen candidate before GPU timing, inspect unreferenced-function diagnostics and the selected call graph, and compare linked SASS with the exact parent. If the modified helper is eliminated and the linked image is byte-identical, preserve the source candidate and build evidence, mark the tuple invalid/inapplicable, restore the parent, and attach a trigger such as a dispatch change that makes the helper reachable. Do not call this a performance rejection, and do not consume correctness or timing budget for an implementation that does not exist in the linked image.
28. **Deduplicate against every prior linked identity.** Index each formal candidate by linked device-code hash as well as source tuple and parent. If a requested tuple produces a distinct source but one member is unreachable, compare the emitted binary with all earlier candidates. A match to a measured subset means the surviving implementation is already adjudicated: bind the subset candidate and compiler-elimination evidence, mark the new tuple invalid, restore the champion, and do not rerun correctness or timing. Reconsider only when dispatch or the eliminated mechanism's active-path implementation changes.
29. **Use dispatch substitution only as a reachability control.** If a mechanism exists only in an unselected helper, a temporary candidate may route the controlling workload through that helper to measure the complete path substitution. Record that result as a control over mechanism plus topology, not as the mechanism's isolated effect. For the actual optimization candidate, restore the accepted dispatch thresholds and helper selection, then transplant the mechanism's semantic lowering into each selected scalar, tiled, paired, or grouped path whose data geometry supports it. Give every path a focused source contract, inspect the selected call graph and linked image, and qualify the exact composition with unchanged host correctness and matched timing. A losing control can reject that route without proving that an active-path transplant will lose.
30. **Split pair-conversion controls by transport and dependency phase.** First preserve the accepted global loader, shared layout, lane ownership, reduction, and output ABI. A physical shared-memory swizzle may make two logical BF16 values adjacent while silently replacing coalesced vector transport; an adjacent-output mapping may instead change reduction and publication ownership. After excluding those confounders, test register packing as key-only and value-only candidates rather than keeping both live. Key packing extends the score recurrence; value packing should be constructed only after score reduction and immediately before numerator updates. Equal register counts and decoded-instruction totals still do not imply equal dependency schedules, so bind linked SASS and let matched timing decide.
31. **Prove physical-device isolation inside the timing lock.** Key one canonical lock by the physical GPU UUID and require every benchmark, profiler, and auxiliary launcher to use it; per-stream or per-tool lock roots do not serialize each other. After acquiring the lock, query the physical device for active compute processes. Start timing only from a zero-process result, and keep the lock through completion. Also inspect scheduler history before adjudication: a later-discovered overlap invalidates latency even if validation passed and the run's own launcher held a lock. Preserve the contaminated artifacts with an invalid label, wait until every overlapping step is terminal, repeat the in-lock audit, and rerun under a unique identity. Never infer a mechanism's effect from an outlier produced during overlap.

### Iterative Full-Monokernel Campaign Contract

Use one row per formal attempt and a separate trigger queue for conditional prototypes:

| Ledger field | Required value |
| --- | --- |
| Candidate identity | Immutable Git revision plus each device-code-affecting source/blob identity |
| Comparison | Exact parent champion, fixed required positions, image, pack, fixtures, grid, warmup, and iterations |
| Objective | Minimum required-position SOL; retain every individual latency/SOL value |
| Correctness | Harness-owned exact decisions/prefixes, mismatch and nonfinite counts, and sealed numerical error statistics |
| Resources | Registers, stack, spills, local memory, static/dynamic shared memory, occupancy, and legal grid ceiling |
| Outcome | Accept, reject, or invalidate, with immutable raw artifact paths, job IDs, and digests |
| Reconsideration | Mechanism, observed failure, controlling position/phase, tested resource state, trigger, and current state |
| Learning boundary | Formal attempt number, lesson disposition, evidence range, and knowledge PR URL when mutated |

The verified campaign demonstrated why the queue is necessary. After an attention restructuring, a recomposed sequential-pair QKV/RoPE fusion that had lost earlier improved all five required positions and raised confirmed minimum SOL from `19.2949%` to `20.0140%` (`+3.73%` relative). Later rechecks of dual accumulation, a global RoPE table, and a dense-load pipeline reversed direction at some short or middle positions but still lost p8191; they remained dormant with new measurable triggers. A padded tensor-core attention path emitted real HMMA instructions and retained two CTAs per SM, yet lost p8191 because useful work per synchronization was too low. These results are compatible: bottleneck changes can revive a mechanism, while the current minimax controller still decides whether the new composition is accepted.

Attempts 26 through 30 sharpened the evidence ordering. Changing 33 logical GQA chunks to 32 preserved the fixed physical 264-task/1,056-partial workspace ABI, the 264-CTA launch, and legal two-CTA residency, but raised the compiled kernel from 96 to 100 registers, increased SASS from 8,960 to 9,056 instructions, and increased IMAD sites from 1,438 to 1,472. Despite those worse static counts, removing the tail chunk raised confirmed p8191 SOL from `26.8088%` to `28.5024%` (`+1.6935` SOL percentage points, `+6.317%` relative), with exact greedy tokens, bit-exact input K/V prefixes, and unchanged harness tolerances. Conversely, a fused-SwiGLU layout that looked positive in a short screen had its apparent p8191/minimum gain reverse in confirmation, and its later composition with direct PTX exponential also regressed at p8191. Static inspection correctly established that the power-of-two candidate was legal; only matched runtime evidence established that it was faster.

Attempts 31 through 35 established a stricter noise boundary. A CTA-local RoPE candidate's two p8191 screens changed direction, so it was rejected before confirmation. A short-tiled attention reconsideration then improved the confirmed minimum from `28.5024%` to `28.8418%`. On that champion, exhaustive dispatch reduced registers from 100 to 90 and decoded SASS from 10,584 to 8,816 instructions; both p8191 screens improved, but 20x200 confirmation regressed the minimum to `28.5910%`, so the screen result was noise rather than a promotion. Composing that dispatch with either fast RoPE power or dense two-chain accumulation produced 96-register binaries with a 32-byte stack, zero local memory, and two CTAs per SM, yet their matched p8191 screens still regressed. These results make the boundary explicit: resource measurements explain a runnable candidate, repeated screens control experiment cost, and correctness plus confirmed performance alone decide promotion or rejection.

Attempt 040 corrected the campaign's adjudication boundary. Its 128-thread grid-396 composition supported three CTAs per SM but used 146 registers and retained three linked-SASS local loads plus two stores. Those diagnostics had originally stopped the experiment. Requalification of the exact CUDA blob passed every host-owned comparison, exact greedy-token and prefix check, then measured `2,457.408` microseconds at p8191, `39.445%` slower than the matched `1,762.272`-microsecond champion screen. The candidate is rejected by measured performance; its register and local-instruction counts only explain the result. Earlier runnable candidates stopped solely by static thresholds must receive the same correctness and performance treatment.

Attempts 044 and 045 completed that treatment for two older static-only prototypes. The exact 101-register dense intra-word ILP binary and 104-register four-live-query attention binary both launched legally at grid 264, preserved exact greedy token and input-prefix bits, and passed every host-owned numerical check. They nevertheless measured `1,918.880` and `1,861.408` microseconds at p8191, regressions of `8.887%` and `5.625%` against the matched attempt-032 screen. This separates two questions that static analysis had conflated: the resource ceiling incorrectly predicted whether the candidates could be evaluated, while runtime correctly established that neither was competitive. Archive resource data as explanation, rerun every legal static-only candidate, and reject only from correctness or measured performance.

Attempts 046 through 050 closed the remaining static-only queue and tested the same evidence boundary on a new optimization. A 106-register staged quad-query candidate and two historical 102-register fast-RoPE candidates all passed unchanged correctness, then regressed matched p8191 by `7.058%`, `6.365%`, and `7.427%`. The warning-emitting direct-`__exp2f` candidate reached H200 execution but failed the host correctness gate before timing, confirming the static warning's prediction without promoting it to the decision metric. Finally, a correct 32-entry RoPE inverse-frequency table removed repeated `powf` source work but regressed p8191 by `0.508%`. Together these results complete the rule: execute every legal candidate; treat compiler and resource evidence as diagnostics; and let unchanged host correctness followed by matched performance decide the outcome of the exact linked binary.

Attempts 052 through 055 verified that reconsideration order is itself part of the composition. Starting from an administratively selected fast-RoPE baseline, dense two-chain accumulation—previously `8.887%` slower as a standalone candidate—improved confirmed p8191 by `0.264%`. Replaying four-query shared K/V reuse on that newly accepted parent—previously `5.625%` slower—then improved the confirmed minimum by another `0.219%`. The related staged two-pair variant still regressed `1.096%`, and the unsupported direct-`__exp2f` spelling still failed host correctness before timing. The durable rule is not that rejected ideas eventually win; it is that each replay must use the current accepted champion, retain its own immutable evidence, and remain independently subject to correctness plus confirmed minimax performance.

Attempts 056 through 060 extended the evolving-champion result and established the shared-lane boundary. Two historical RoPE replays were exact no-ops and were invalidated without timing. Replaying the constant inverse-frequency table on the current champion then improved confirmed p8191 by `0.345%`; reusing one per-token sine/cosine table across all layers improved it by another `0.116%`. After qualification moved from a dedicated H200 allocation to physical GPU 6 of a non-exclusive eight-GPU Warden node, the unchanged champion was reconfirmed in that serialized lane before testing the next candidate. Copying the accepted global RoPE table into a dedicated CTA-shared array passed every host-owned correctness check but regressed the matched p8191 screen by `0.482%`. The verified rule is twofold: advance replay parents only after confirmation, and re-establish the comparator whenever node or exclusivity changes; neither lower source work nor closer memory locality substitutes for matched runtime evidence.

A later verified checkpoint isolated per-iteration attention metadata placement. Keeping the complete small online-softmax state in registers removed repeated shared-memory publication and improved the confirmed minimax result while slightly reducing the linked register allocation. Moving only the normalization half back to shared memory passed the same host correctness policy but increased linked registers and lost the first matched performance screen. This is compiler-liveness evidence, not a universal ban on shared state: the durable rule is to freeze, inspect, and time each placement, including its address-state lifetime and hot-loop traffic.

A subsequent checkpoint tested several ways to reduce hot attention instructions and source-level liveness. Separating key scoring from value updates and compile-time-specializing the update path remained close but did not improve matched timing; their combination lengthened the staged dependency schedule. Fusing independent K/V tile-load loops substantially reduced linked instructions and slightly reduced registers but lost runtime, consistent with reduced memory-level parallelism. Hoisting one invariant 64-bit tile address produced the opposite compiler result: allocation and instructions expanded sharply. The reusable rule is to optimize the emitted dependency and issue schedule, not source arithmetic or static totals in isolation.

The next checkpoint isolated source-equivalent control effects. Narrowing an address accumulator did not rescue an earlier hoist, and removing a runtime load plan shortened the linked binary substantially without improving latency. More sharply, deleting a provably redundant hot-loop predicate preserved the aggregate register, spill, shared-memory, and decoded-instruction counts while changing the linked instruction stream and causing a large matched slowdown. Reversing the operands while keeping both predicates was much closer but still lost. Logical equivalence and aggregate resource equality are therefore insufficient: preserve an exact device-code identity, inspect instruction ordering, and time each control spelling as its own candidate.

The following checkpoint tested source changes commonly assumed to lower register pressure. Carrying a cheap loop index explicitly was slightly slower, and composing it with another near-neutral lifetime change produced a much worse dependency schedule. Narrowing one bounded query offset expanded linked allocation and introduced local traffic. Most decisively, partial unrolling of a fixed four-record update prevented full scalarization and materialized indexed state through a sizable stack-backed load/store sequence, producing a severe measured slowdown; spelling the full trip count explicitly removed that stack signature but still changed scheduling and lost. The reusable rule is to inspect scalarization and linked local traffic after index or unroll changes, while preserving correctness and performance as the only acceptance metrics.

The next composition checkpoint exposed two distinct identity hazards. First, repeated attention-source patterns allowed a mechanically recovered predicate delta to land in the wrong path until a phase-anchored contract rejected it before GPU qualification. Second, one correctly scoped control rewrite emitted the same linked SASS and resource report as its parent but still lost its matched screen, reinforcing that device-code identity is provenance and explanatory evidence rather than a timing waiver. In the same checkpoint, two mechanisms that had each been individually near-neutral combined into a small confirmed minimax improvement. Composition therefore needs both source-level proofs that every named mechanism remains active and binary-level binding of the exact executable, while unchanged host correctness and matched measurements alone decide promotion.

A later checkpoint used control composition to localize a repeated loss. Several tuples shared one mutually exclusive data-preparation alternative, while their partner mechanisms targeted different phases. The simplest control retained the accepted hot-loop schedule and changed only that alternative; it also lost its first matched screen. Adding a source-level predicate variant produced byte-identical linked SASS to the control. This separated two claims that the earlier combinations could not: the shared alternative was the dominant current cost, and the predicate partner did not survive compilation. Further combinations containing the alternative should be deprioritized unless another mechanism can remove or hide that measured cost, but every valid runnable tuple remains subject to the unchanged correctness and timing policy.

The following checkpoint sharpened that control analysis. One partner compiled to the same device code as the losing shared-replacement control, while another produced a distinct instruction stream and narrowed the control's loss without overtaking the accepted champion. The first interaction was compiled away; the second was a partial rescue, not a win. Record both champion-relative and control-relative deltas so acceptance remains stable while reconsideration can prioritize mechanisms that demonstrably offset part of a shared cost.

The next checkpoint exposed an address-space composition failure. A read-only global-load delta was initially layered onto a candidate that still routed projection through a mutually exclusive shared table. Compilation succeeded, but host-owned execution rejected the shared address before correctness or timing. Rebuilding the tuple with the shared declaration, copy, and call-site argument removed—and proving the global workspace pointer reached both loads—produced a runnable, correct binary. The durable rule is to bind storage provenance as part of mechanism identity: an intrinsic's source spelling does not establish the address space it will consume.

The following checkpoint tested several compositions around one recurring compute-schedule change. Different partners failed to remove its dominant cost, and one composition sharply reduced aggregate linked instructions and registers while producing the largest matched slowdown in that group. Much of the static reduction came from removing alternative dispatch code, not from shortening the selected hot path. This strengthens the diagnostic boundary: classify static changes by phase and selected control path, and never increase confidence in a speedup merely because the whole binary became much smaller.

A subsequent composition checkpoint showed that even a measured partial rescue is conditional. One mechanism had narrowed the loss of a costly control in one exact tuple, but when paired with a different source-equivalent control change on the accepted schedule, the resulting candidate passed correctness and lost substantially. Another source change emitted byte-identical device code to its control in a separate tuple, so the observed timing difference could not be attributed to that source mechanism. Interaction labels must therefore be keyed to parent, partner set, and linked binary: they rank exact recompositions, not mechanisms in isolation.

The next checkpoint separated source activation from linked implementation identity. An exact historical delta changed only a paired-query attention helper, and focused contracts proved the delta plus all inherited mechanisms remained in source. The active long-context dispatch instead selected a quad-query helper. The pinned compiler reported the modified function unreferenced and emitted a whole-image SASS hash identical to the measured parent, so the tuple was invalidated before correctness or timing and the exact parent was restored. This does not weaken the rule that resources cannot reject a distinct runnable candidate: it prevents a source-only no-op from masquerading as a new implementation and consuming qualification budget.

The following checkpoint extended that identity rule beyond parent comparison. A source tuple combined one mechanism in an unreachable dispatch alternative with an independently materialized mechanism in another phase. The compiler eliminated the unreachable member, so the linked binary differed from the champion but was byte-identical to the earlier candidate containing only the surviving mechanism. The tuple was invalidated without repeating correctness or timing. Campaign deduplication must therefore index every prior linked implementation and identify the surviving subset, not merely compare a candidate with its immediate parent.

The next checkpoint separated reachability controls from optimization candidates. Redirecting the controlling long-context workload from its accepted grouped path to an older paired path made a historical adjacent-vector mapping reachable and passed unchanged host-owned correctness, but matched timing regressed substantially. That result rejected the complete route substitution; it did not isolate the mapping from the topology change. The follow-up experiment must restore the accepted dispatch and express the mapping directly in each applicable active path, with path-specific source contracts and linked reachability evidence.

The follow-up checkpoint decomposed that active-path vectorization idea. Changing logical adjacent ownership lost because it altered reduction and output publication. Preserving ownership through a physical shared-tile swizzle lost more because the swizzle replaced the accepted vector global transport. Register-packing the original logical pair while retaining transport also lost, even with the same aggregate register and instruction counts, so the conversion schedule was split again. Key-only packing remained a clear regression, while value-only packing after score completion was near-neutral. The reusable rule is to treat transport, ownership, score recurrence, and value lifetime as separate mechanisms; prioritize the value-only variant for objective reconsideration, but do not promote it without positive matched screens.

A verified multi-query prefill checkpoint exposed a separate numerical identity hazard. A candidate and a sequential comparator disagreed in a tiny fraction of cancellation-sensitive BF16 cache projections while model outputs remained within the frozen contract. Independent reference checks showed that the comparator, not the candidate, owned those cache failures. Replacing online FP32 softmax state with two-pass accumulation, FP64 normalization, FP64 numerators, or both did not monotonically approach the reference; vectorized framework reductions also changed the failing elements. The reusable rule is to freeze the reference's reduction semantics, validate all cache rows at context boundaries, and treat arithmetic topology as an experimental mechanism rather than assuming more precision or a familiar framework kernel is more correct.

A verified shared-node checkpoint exposed a physical-device isolation hazard. Two launchers each serialized their own work, but their different lock namespaces allowed them to use one physical GPU concurrently. The overlapped candidate retained correct outputs while producing a large latency outlier. After the overlapping step became terminal, a rerun performed a zero-compute-process audit while holding one canonical physical-UUID lock and returned to the expected timing scale. The reusable rule is to bind every launcher to one physical-device lock namespace, audit actual compute-process state inside that lock, and invalidate rather than interpret any timing with proven overlap.
